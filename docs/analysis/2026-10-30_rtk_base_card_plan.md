# RTK base card: plan (2026-10-30)

Goal: an end user pairs the Tron with the vendor LoRa RTK base from the web app
(Settings → GPS & Positioning) instead of `scripts/rtk_pair.py` over ssh. The card must
send the same bytes as the script: `$GLIST,<band>`, 0.5 s, `$GNCON,<addr %04X>,<chan %02X>`,
then read back with `$GNCON,0000,FF*4B`.

## What exists

- `um960_gps_driver` already offers `/mower_gps_node/set_lora` (`mower_interfaces/srv/SetLoRa`),
  but it is a logged stub unless `lora_pairing_enabled: true` and returns `true` once the
  bytes are written, with no read-back. It stores `$GNCON` replies in `_lora_pairing`;
  `$GLIST` replies are not routed to the rover-line handler.
- The GUI already has `POST /api/corrections/lora/pair` and `GnssCorrectionSourceCard`
  (Settings → NTRIP, shown only while the correction source is LoRa). It needs the base
  serial and has no read-back, status or region names. It stays as it is.
- foxglove_bridge streams only `FOXGLOVE_GUI_TOPICS` (`launch/mower.launch.py`), and
  `src/mower_bringup/test/test_foxglove_whitelist.py` checks that list against the GUI's
  `topicMap`. Services are not filtered.

## ROS side

1. `mower_interfaces/srv/GetLoRa.srv`: empty request; response `bool ok, uint16 addr,
   uint8 channel, string band, string raw, string message`.
2. `lora.py` (ROS-free): `BASE_RESET = "$BRESET*17"`, `parse_gncon()`, `parse_glist()`,
   `BAND_NAMES`, `validate_pairing(addr, channel, area)` (addr 0..0xFFFE, channel 1..75,
   area in 00/01/02/03/F, "" still allowed for the vendor BLE path that derives the band
   from the serial).
3. `um960_node.py`:
   - `$GLIST,` lines go to `_consume_rover_line`, stored as `_lora_band`; each `$GNCON`/
     `$GLIST` reply bumps a counter under a `threading.Condition` so a service can wait
     for "a reply newer than my query".
   - `get_lora` (`/mower_gps_node/get_lora`): write the query, wait up to 1.5 s for
     `$GNCON` and up to 0.5 s more for `$GLIST`. Allowed in any correction mode (read-only
     on the board) when pairing is enabled.
   - `set_lora`: `lora_pairing_enabled` defaults to **true**; validation as above; after
     the writes it re-queries and returns `result = stored == requested`.
   - `reset_base` (`std_srvs/Trigger`): writes `$BRESET*17`; only in LoRa mode, like
     `set_lora`.
   - The three services get their own callback group and `main()` uses a
     `MultiThreadedExecutor`, so a 2-3 s pairing does not stall the 10 Hz `/fix` timer.
     Timers keep the default (mutually exclusive) group, so their behaviour is unchanged.
   - `/mower_gps_node/lora_status` (`std_msgs/String`, 1 Hz JSON):
     `{pairing:{addr,addr_hex,channel,band,band_name}|null, ref_station, nrtk_on,
     station_id, diff_age_s, fix_type, correction_source, rtcm_source, pairing_enabled}`.
4. `launch/mower.launch.py`: whitelist `^/mower_gps_node/lora_status$`.
5. Tests (`test/test_lora.py`, `test_corrections.py`): command bytes (`$GLIST,2*5B`,
   `$GNCON,9527,28*48`, `$BRESET*17`), parsing, validation, get_lora / set_lora read-back
   against the pty harness, reset_base gate, lora_status JSON.

## GUI backend (`pkg/api/rtk_base.go`)

- `topicMap["rtkBaseStatus"] = /mower_gps_node/lora_status` (std_msgs/String).
- `GET /api/rtk-base/status`: latest status JSON (lazy subscription, waits up to 2 s for
  the first message, 503 if none).
- `GET /api/rtk-base/pairing`: calls `get_lora`, returns addr (decimal + hex), channel,
  band + name.
- `POST /api/rtk-base/pair` `{addr, channel, area}`: addr as number, decimal string or
  `0x` hex string; validated as on the ROS side; calls `set_lora` with `sn=""`.
- `POST /api/rtk-base/reset`: calls `reset_base`.
- "service not advertised" → 503, as in `corrections.go`. Go tests with `MockRosProvider`.
- No tygo step: tygo only covers ROS message packages; the web uses `guiApi.request` with
  local types, as `GnssCorrectionSourceCard` does. The swagger docs (`gui/docs/`) are
  regenerated by hand upstream and are left as they are; the routes carry `@Router`
  annotations for the next regeneration.

## Web

- `robotProfiles.ts`: feature `lora_rtk_base` (upstream false, AirseekersTron true).
  `profileGates.ts`: `feature:rtk_base` → `lora_rtk_base`.
- `utils/rtkBase.ts`: pure helpers (addr parsing, regions, universal code, status parse).
- `components/settings/RtkBaseCard.tsx`, rendered by `PositioningSection` when the gate
  is visible: stored pairing, live status (via `useTopic("rtkBaseStatus")`), NTRIP
  warning, form (address, channel, region), Use universal code, Pair (confirm dialog),
  Read from board, Reboot base, help text. Works at 390 px (single column on xs).
- i18n strings in `en.json` (other locales fall back to English).
- Tests: `rtkBase.test.ts`, `RtkBaseCard.test.tsx`, profile/gate tests updated.
