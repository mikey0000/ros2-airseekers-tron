## 3. MowgliNext: imported, and deliberately different

**Imported or ported** (GPL-3.0; vendored with `LICENSE` and `UPSTREAM_COMMIT` under `third_party/mowglinext`, ignored by colcon):

- **GUI**: used as is, with upstreamable Tron profiles and gating (`docs/gui_tasklist.md`, `web/src/constants/profileGates.ts`), plus `mower_gui_bridge` to expose `/hardware_bridge/*` and `/gps/*`.
- **`mowgli_interfaces`**: vendored verbatim in `src/mowgli_interfaces`.
- **Map server**: `mowgli_map` was ported to Python as `src/mower_map`.
- **Mission**: the `mowgli_behavior` main tree, FollowStrip, coverage persistence (the resume file format is upstream-compatible, `mowgli_coverage_resume v2`) and recording were ported to `src/mower_mission`. State codes and `state_name`s match upstream.
- **Coverage action**: the `PlanCoverage` contract is served by `src/mower_coverage_bridge`. The planner structure (ConstHL rings, then BruteForce/NSwath, then mainland) mirrors `mowgli_coverage`.
- **Controllers**: `FTCController` (including `obstacle_deviation.hpp`) and `PathProgressGoalChecker` were backported Kilted to Humble in `src/mowgli_nav2_plugins`.
- **Control**: `cmd_vel_slew`, `dig_detector` (now `slip_detector`) and the IMU calibration pattern went into `src/mower_control`. The teleop WebSocket relay went into `src/mower_teleop`.
- **Settings**: `config/gui/mowgli_robot.yaml` (device-owned) drives ROS parameters live.

**Deliberate deviations** (each marked `DEVIATION:` in `src/mower_navigation/config/nav2_params.yaml` or in the package READMEs):

| Deviation | Reason |
|---|---|
| EKF (`robot_localization`) instead of the GTSAM iSAM2 `fusion_graph` | GTSAM needs an aarch64 source build, and there is no LiDAR for scan matching. Wheel odometry, IMU and RTK is a case an EKF handles well. |
| Python FSM instead of a BehaviorTree.CPP tree | Humble ships BT.CPP v3 and the upstream tree is v4. The guard order is kept the same. |
| `mower_docking` actions instead of opennav `DockRobot` and `BackUp` | Humble `nav2_msgs` has no `DockRobot`. The vendor reverse-ArUco docking is the reference. |
| No `collision_monitor` | No scan source exists, so it would pass everything through. |
| NavFn instead of SmacPlanner2D | Chosen for an empty or static global costmap. Revisit for go-around (§5). |
| Plain RPP with rotate-to-heading instead of RotationShim(RPP) for transit | One fewer plugin to tune. |
| `robot_base_frame` is `base_link` (rear axle) | Vendor frame convention. |
| Unstamped `Twist` everywhere | Humble `twist_mux` and Nav2 have no stamped mode. |
| Controller at 20 Hz, smaller costmaps | Matched to a 0.3 m/s robot and the CPU budget. |
| FTC `speed_angular` 15°/s and `max_cmd_vel_ang` 0.3 | MCU clamp of 0.3 rad/s. Measured about 0.2 rad/s in turf. |
| Coverage on F2C 2.1 (apt) instead of 3.0 (source build) | See §4. |
| Not ported: LiDAR guards, escape and dig manoeuvres, cross-hatch, `CRITICAL_BATTERY_*`, retiring an area after 5 dispatches, `get_recovery_point` navigation | No LiDAR, simpler failure handling. Boundary recovery transits 1 m ahead on its own sub-path instead. |
| Soft boundary violations pause only while mowing, never during a transit | Avoids stalls on blade-off transits that clip a boundary. |

## 4. Fields2Cover v3: worth it?

**What we use now** (`src/mower_coverage`, `CMakeLists.txt` `find_package(Fields2Cover 2.1.0)`, apt `ros-jazzy-fields2cover` 2.1.0, OR-Tools via `ros-jazzy-ortools-vendor`):

- Headlands use `f2c::hg::ConstHL`, one call per ring. Rings are chained backwards so that they hand over without a transit.
- Swaths use `f2c::sg::BruteForce` with `f2c::obj::NSwath`. AUTO angle uses a 5° step, with the longest edge above 400 m².
- Route and order: F2C's `BoustrophedonOrder` is not used, because it alternates between pieces of a sweep line around holes. The planner uses its own sweep-cell decomposition (`buildSweepCells`), cell ordering (`orderCells`) and a serpentine inside each cell. No Dubins or Reeds-Shepp turn planner is used. Turns are left to the controller, with swath U-turns about 0.18 m.
- Obstacles: holes are cut from the cell. Hole rings plus a band act as keep-outs, and transits at gaps over 0.6 m become blade-off transits (`mower_coverage_bridge/splitter.py`).
- Modes: `zigzag`, `spiral` and `contour_only` (rings only). `cross` and `alternate` are handled by re-planning at angle offsets in `mower_mission`.

**MowgliNext on v3** (`third_party/mowglinext/mowgli_coverage/CMakeLists.txt`): it pins `find_package(Fields2Cover 3.0.0)`, built from source into `/opt/fields2cover-300`, and needs an `ortools::ortools` CMake workaround. In its `coverage_planning.cpp` it uses the same primitives: `ConstHL`, `BruteForce`, `NSwath`, `BoustrophedonOrder`.

**What the web check found** (low confidence; GitHub releases and docs at fields2cover.github.io):

- The latest tagged GitHub release is 2.1.0 and the docs site shows 2.1.1. No v3 release notes or migration guide were found. The "3.0.0" MowgliNext pins is probably a main-branch version, but this is unconfirmed; check the tags before relying on it.
- Main and 2.1.x offer `ReqHL` (per-border headland widths), `CorridorHL`, boustrophedon and trapezoidal decomposition for non-convex fields and obstacles, OR-tools route optimisation, snake and spiral orders, Dubins and Reeds-Shepp turns including continuous curvature, and a one-call `planCovPath`.
- Packaging: no Humble binary for 3.x. A source build on arm64 pulls OR-Tools, GDAL, GEOS and TBB. It is slow on the RK3588, so build it in an x86 cross or multi-stage image. CMake also needs the ortools target workaround.
- API: v1 to v2 renamed many methods. Whether 2.1 to 3.0 breaks the API further is unknown. MowgliNext's code suggests it is small, because it uses the same class names.

**Assessment.** For this lawn use case, F2C v3 would not be a meaningful improvement.

- The parts that matter on a lawn (ring chaining, ordering around holes, fewer transits, ring sanitisation) were written ourselves on top of F2C because F2C's own ordering was worse. v3 would not replace that code.
- Turn planners (Dubins or continuous curvature) are built for tractors. A differential-drive mower turns in place or on 0.18 m U-turns, and FTC or RPP handles that.
- OR-tools route optimisation matters on many-cell fields. Our `orderCells` already minimises transits. Its benefit is unproven at lawn scale.
- `ReqHL` (per-edge headland count) would be nice for walls versus open edges, but it is reportedly also in 2.1.x. Check this first.
- The cost is real: a source build with OR-Tools on arm64, a CMake workaround, and the loss of the apt package.

**Recommendation:** stay on apt 2.1.0. Revisit only if (a) a field shape defeats `buildSweepCells`, at which point try F2C's boustrophedon decomposition from 2.1 first, or (b) a Humble or Jazzy binary of 3.x appears. If the stack moves to a newer ROS distro, reconsider then.

## 5. Obstacle avoidance: does the mower need to go around?

**Today:**

- **Detection**: bumper (MCU hard stop, then `bumper_controller` backs up and rotates, then `/bumper_cloud`), stereo-ranged YOLO points (`/ai/det/obstacle_points`, local costmap), `obstacle_guard` (stop and blade off for persons and pets inside range), and dig/slip.
- **Response on swaths**: RPP collision detection aborts the goal. The mission retries (`follow_retries` 3, costmaps cleared, 3 s apart) from the last pose, then skips the sub-path, and the session may end in `MOWING_INCOMPLETE`.
- **Response on transits**: Nav2 replans with NavFn, with 3 transit retries.
- **FTC** (`FollowCoveragePathFTC`, opt-in) has an `obstacle_deviation` port: lateral offset up to 1.5 m, confined to the zone, plus wait (2.5 s), clear-hold and a short reverse.

**Is "go around" needed? Yes, but only a limited version, and only for static obstacles.**

- **Dynamic obstacles** (people, pets, hedgehogs) should never be driven around with the blade on. The correct behaviour is stop, blade off, wait, and resume when clear. That is what `obstacle_guard`, the FTC wait and the mission retry already do. Do not let the deviation logic act on these classes.
- **Static obstacles** (furniture, toys, a hose, a ball) are common, and they persist for the whole run. With stop-and-retry, each one costs three retries and then the rest of the sub-path. Because a sub-path is a whole serpentine group, one chair can leave a large unmown band. That is the real gap.
- **Mowing around versus skipping and returning later.** Going around costs a few metres of blade-off driving and leaves a small unmown ring around the object. Skipping loses the rest of the swath group. Returning later only helps if the object moves, and the mission does not yet re-queue skipped pieces.
- **MowgliNext** relies on FTC lateral deviation plus LiDAR collision monitor guards, and retires an area after 5 dispatches without progress. It does not plan detours around the obstacle.

**Recommended design** (in order):

1. **Make FTC the coverage controller** (`config/mission.yaml` `follow_controller_id: FollowCoveragePathFTC` with `coverage_goal_checker_ftc`) once the 2026-10-06 tuning is confirmed on more swaths. This alone gives small lateral detours up to 1.5 m inside the zone, and it removes the premature-success workaround. Effort: about 1 day plus field tests.
2. **Class-aware gating**: obstacle points from person, pet or animal classes go to a "dynamic" source that only triggers stop and wait (guard or FTC wait, never deviate). Static classes and stereo or bumper points feed the deviation layer. Effort: 1-2 days (`det_range` publishes two clouds, plus two costmap observation sources).
3. **Swath detour in the mission** when FTC deviation fails, meaning the obstacle is wider than 1.5 m or sits on a swath end. Blade off. Take the next sub-path pose beyond the obstacle footprint plus margin. Plan with SmacPlanner2D (or NavFn) on the local and global costmap with the obstacle marked, `/navigate_to_pose` around it, then resume `FollowPath` from that pose (the resume tracker already supports "continue from pose"). Cap at one detour per obstacle. Record the skipped stretch. Effort: about 3-5 days including tests.
4. **Re-queue skipped stretches** at the end of the area pass: one blade-off transit and one retry each, then give up and report `EncounterObstacles`, matching vendor IotNotice 900027, "obstacle cannot be bypassed, user intervention". Effort: about 2 days.
5. **Optionally promote persistent obstacles** to map obstacles (`promote_obstacle` already exists, pending to accepted) so the next plan cuts them as holes. Effort: about 1-2 days.

The vendor stack evidently had a bypass: `IotNotice` 900027 exists, and TEB served as the task controller. The closed implementation was not recovered. Total for steps 1 to 4 is about 1.5-2 weeks, most of it field testing. Nav2 `nav2_behaviors` spin and backup are not a go-around; keep them for recovery only.

## 6. Motion safety requirements

Another agent is implementing a motion gate at the same time. This section records the requirement and the intended design only.

**Requirements (from the owner):**

1. The wheels never move outside mission motion states: autonomous `UNDOCKING`, `TRANSIT`, `MOWING`, `RETURNING_HOME` and docking, plus operator `RECORDING` and `MANUAL_MOWING` (joystick). In particular, no motion from IDLE, EMERGENCY, CHARGING or the failure states.
2. The wheels never move while docked until an undock has been commanded.
3. An emergency reset (`RESET_EMERGENCY` 254, `/clear_estop`) never releases a stale command. After a reset the robot stays still until a fresh command arrives from an authorised source.

**Current gaps:**

- Several publishers can move the wheels independently of the mission state:
  - `bumper_controller` (lane 50; it backs up on any bumper hit, even when idle or docked)
  - the teleop relay (lane 20) and `base_ble`
  - `mower_docking` (lane 15)
  - Nav2 (lane 10)
- `twist_mux` only knows the `/estop` lock, not the mission state.
- `/clear_estop` drops the MCU latch. Any lane still being published within its timeout would then pass through, for example a joystick held during the emergency, or a Nav2 goal that was not cancelled.

**Intended design:**

- **One gate at a single choke point**: between `twist_mux` and the MCU, either in `cmd_vel_slew` or as a host-side check in `mcu_node`, so no lane can bypass it.
- **Inputs**: a latched `motion_allowed` (or allowed-lane set) published by `mower_mission` from its state. Undock clears the docked latch.
- **Docked check**: docked is true when `is_docking_done` or `is_charging` is set. While docked, the gate refuses everything except the undock lane during `UNDOCKING`.
- **Default deny**: if the mission state is missing or stale (more than about 1 s), block all motion.
- **Re-arm after reset**: when the e-stop clears or the mission leaves EMERGENCY, the gate requires a rising edge. Every lane must first see a zero or no command, or a new message newer than the reset time, before any non-zero command passes. The mission sends nothing after a reset (no auto-resume, already the case). The relay and BLE need a fresh press.
- **Exceptions**: the bumper back-off is allowed only in mission motion states. Otherwise a bumper hit only stops. The zero bursts on `/cmd_vel_emergency` always pass.
- **Silence**: when the gate blocks, the driver sends the standard 3 zero frames and then stays silent, per `docs/wheel_control_semantics.md`.
- **Tests**: a table-driven test of the gate (state × lane × docked × reset edge). Extend the mission randomised test to assert that no non-zero `/cmd_vel` occurs outside the allowed states.
