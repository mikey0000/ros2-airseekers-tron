# UM960 GNSS/RTK driver

`ros2_stack/src/um960_gps_driver` — a dependency-light ROS 2 Humble driver for the
Unicore **UM960** receiver on the Airseekers Tron mower. It replaces the vendor's
closed `mower_gps_driver_node` (`05_driver_binaries/nodes/mower_gps_driver_node`,
ROS 1 Noetic, Chinese vendor tree `base_rtk/mower_gps_driver`).

## Hardware and port

| | |
|---|---|
| Receiver | Unicore UM960 (multi-GNSS RTK), behind an Artery AT32 `rtk_rover` board + LoRa M4 |
| Device node | `/dev/serial_rtk` |
| UART | `ttyS4`, UART4 @ `0xfeb70000` |
| Settings | 115200 8N1, no flow control (vendor: `base_rtk/mower_gps_driver/config/mower_rtk.yaml`) |
| Framing | NMEA 0183 + Unicore ASCII logs + Unicore binary synch `AA 44 B5` |

The udev rule lives in `07_system_config/udev/mower.rules`. On a dev machine without
that symlink, pass `port: /dev/ttyS4` instead.

> Nothing was run against the real mower while writing this. Stop the vendor driver
> before starting this node: `mower-base.service` launches
> `mower/launch/mower_base.launch` → `base_rtk/launch/base_rtk.launch` →
> `mower_gps_driver/launch/base_rtk.launch`, i.e. it owns the GNSS port. Two readers on
> one UART corrupt the stream for both.

## What the receiver emits

From `strings libmower_gps_driver.so` and
`base_rtk/ntrip_client/scripts/serial_rtk_config.py`, the vendor configures the port with:

```
freset
MODE ROVER
CONFIG RTK TIMEOUT 20 RELIABILITY 4
CONFIG DGPS TIMEOUT 12
GPGGA com1 0.2      # 5 Hz
GPRMC com1 0.2
GPVTG com1 0.2
GPHPR com1 0.2
BESTNAVA 5         # 5 Hz  <- the vendor's primary fusion log
saveconfig
```

Note the 0.2 s rate: roughly 5 sentences/s plus ~200-byte BESTNAVA frames is ~16 kbit/s,
comfortably inside 115200 (their note is "115200 baud ⇒ at most 57 packets/s"). The same
vendor tree bumps the port to 921600 in `ntrip_client/config/metal-2.yaml` and writes
`config com1 921600` when injecting corrections at full rate.

### Log set this driver handles

**NMEA / Unicore ASCII** (checksum-validated, `$`-prefixed):

| Sentence | Used for |
|---|---|
| `GNGGA` / `GPGGA` | position, altitude, fix quality, sats, HDOP, RTK age, base station id |
| `GNRMC` / `GPRMC` | UTC date+time, fix validity, speed over ground, course |
| `GNVTG` / `GPVTG` | course and speed (preferred over RMC when both are on) |
| `GNGSA` | fix dimension (2D/3D), DOP triple, satellites used |
| `GPGSV` | satellites in view, best SNR |
| `GPGST` | pseudo-range error statistics (HDOP only) |
| `GPHPR` | Unicore heading log — the true-heading source for `/heading` |

**Unicore proprietary ASCII** (`$GNxxx`, dispatched on the whole message id, not the
NMEA suffix):

| Log | Meaning |
|---|---|
| `$GNVER` | receiver / hardware / firmware versions |
| `$GNSTA` | reference-station status (`FINE` when differential data is live, `FAIL` otherwise) |
| `$GNCON` | constellation / correction configuration |
| `$GNREF` | reference station id and description |
| `$GNRTK` | NRTK (network RTK) switch; `switchNRTK()` in the vendor library sends `$GNRTK,ON*69` or `RTKRESET`, and `$GNCON,0000,FF*4B` / `$GNVER,*64` to poll constellation and version |
| `GHARDM` | hardware status (antenna, self-test, supply) |
| `BESTNAV` / `BESTNAVA` | the full solution (see below) |

`BESTNAV` carries everything the fusion filter wants: solution status, position type,
lat/lon/height in decimal degrees, per-axis sigma, differential age, satellites
tracked/used, velocity type, horizontal/vertical speed, track angle and latency. This is
the log the vendor's fusion code consumes; when it is present this driver uses its accuracy
numbers in preference to the HDOP-derived estimate.

**Unicore binary synch** (`AA 44 B5 <id> <len_lo> <len_hi> <payload> <crc16_lo> <crc16_hi>`):

- CRC-16/XMODEM (poly `0x1021`, init `0`) over message id + length + payload.
- `0x0A` **BESTNAV** — decoded fully: lat/lon as int64 ×1e-8, height as int32 ×1e-4,
  sigma as float32, station id as 4 chars, plus undulation/datum, satellite counts,
  velocity type, speeds and track angle. Anything shorter than the last decoded offset
  (`H+120`) is ignored rather than half-parsed.
- `0x01` **VERSION** — ASCII version string.
- Other ids are counted (`parser.message_counts`) rather than decoded, so you can see
  what the receiver is actually streaming after a `CONFIG` change.

Binary frames and ASCII sentences **interleave on the same port**. `Um960StreamSplitter`
keeps one buffer and hands it to whichever framing comes first in byte order, so partial
frames spanning two `read()` calls are handled and the freshest solution wins when the two
disagree.

## Topics

| Topic | Type | Notes |
|---|---|---|
| `/fix` | `sensor_msgs/NavSatFix` | `frame_id` = `gps`. `status.status` from GGA quality (0 no-fix, 1 GPS, 2 DGPS, 4/5/6 → `STATUS_FIX`) and from the BESTNAV position type. Covariance from the receiver's own sigma when available, otherwise HDOP × 1.2 m UERE; `COVARIANCE_TYPE_UNKNOWN` when there is no accuracy information at all (better than a fictitious perfect fix). |
| `/vel` | `geometry_msgs/TwistStamped` | body-frame x = ground speed, sign-flipped when the track angle is in the southern half (mower convention). |
| `/heading` | `std_msgs/Float32` | **degrees**, true north, normalised to `[0, 360)`. From `GPHPR` if the receiver sends it, else the track over ground. |
| `/fix_status` | `std_msgs/String` | human-readable summary: `um960=connected solution=NARROW_INT sol_status=SOL_COMPUTED vel_type=DOPPLER_VELOCITY sats=18/21 hdop=1.05 diff_age=0.5s station=BAS1 ref=FINE gsa=PPM_FIX corr_src=lora corr=lora corr_flow=active corr_age=0.5s age=0.02s` |
| `/nmea` | `std_msgs/String` | raw ASCII lines, off by default (`publish_nmea: true`). Useful for debugging. |
| `/gps/corrections` | `std_msgs/String` | 1 Hz JSON correction diagnostics (see "Choosing the correction source"). |

Service: `/mower_gps_node/set_lora` (`mower_interfaces/srv/SetLoRa`, offered when
`mower_interfaces` is installed) — vendor LoRa base pairing, a logged stub unless
`lora_pairing_enabled: true`.

The vendor also published `/unicore_nav` (`mower_gps_msgs/UnicoreNav`), `/ref_origin`,
`/gps_dev_status`, `/mower_gps_node/{info,ref_info,nmea}` and the services
`/mower_gps_node/{ntrip,set_lora,ref_reset,set_nrtk_bind}`. Of those only `set_lora` is
reproduced; NTRIP is configured by parameters instead of the `ntrip` service.

Nothing is published when no fix has been seen, or when the last one is older than
`fix_timeout_s` — in the latter case `/fix_status` keeps publishing, prefixed with
`STALE`, so you can tell "the receiver went quiet" apart from "the node is dead". A
`GNGGA` with quality 0 or an `RMC` with a `V` status also clears the position, so a lost
fix stops `/fix` instead of repeating a stale coordinate.

## Parameters

| Parameter | Default | Meaning |
|---|---|---|
| `port` | `/dev/serial_rtk` | serial device |
| `baud` | `115200` | baud rate (`921600` if you reconfigure for binary-heavy logs) |
| `frame_id` | `gps` | `NavSatFix` / `TwistStamped` frame |
| `publish_rate_hz` | `10.0` | matches the vendor's measured 10 Hz `/fix` |
| `fix_timeout_s` | `2.0` | stop publishing `/fix` after this long without a solution |
| `serial_timeout_s` | `0.2` | per-read `select()` timeout |
| `reconnect_period_s` | `2.0` | retry delay after a read/open failure |
| `sane_lat_limit` / `sane_lon_limit` | `90.0` / `180.0` | refuse to publish impossible coordinates |
| `publish_nmea` | `false` | mirror raw ASCII to `/nmea` |
| `config_commands` | `[]` | receiver commands written once on (re)connect; **empty by default** |
| `correction_source` and `ntrip_*` | | see "Choosing the correction source" |

`port`, `baud`, `frame_id`, `fix_topic`, `vel_topic`, `heading_topic`, `fix_status_topic`
and `nmea_topic` are all overridable so the node can be relocated into a namespace.

## Choosing the correction source

Without RTCM corrections the UM960 gives a single-point fix (`solution=SINGLE`,
metre-level). There are two ways to feed it. **Only one source ever writes RTCM**,
selected with `rtcm_source` (preferred) or the legacy `correction_source`:

| `rtcm_source` | Behaviour |
|---|---|
| `auto` (default) | NTRIP while the caster delivers CRC-valid RTCM (last valid frame ≤ `ntrip_fallback_grace_s`, 5 s), otherwise the LoRa base. NTRIP runs only when *enabled* (see the settings file below). Hand-over to NTRIP = `RTKRESET` + `$GNRTK,ON*69` + keep-alive; hand-back = stop the keep-alive (the board returns to LoRa in ~6 s; no OFF command is sent, the vendor never sends one). |
| `ntrip` | NTRIP only; the board is held in network-RTK mode even while the caster is down (LoRa locked out). |
| `lora` | LoRa base only; the host never writes corrections. |
| `none` | nothing is written. |
| `""` | use `correction_source`: `ntrip`/`lora`/`none` as below, `""` = `auto`. The GUI NTRIP switch still drives `correction_source` (`true` → `ntrip`, `false` → `lora`, param_bindings.go). |

Legacy `correction_source` values:

| `correction_source` | Path | Host writes to `/dev/serial_rtk`? |
|---|---|---|
| `lora` | vendor RTK base station → LoRa → `rtk_rover` board → UM960 | **no** (only `set_lora` pairing, and only with `lora_pairing_enabled: true`) |
| `ntrip` | your NTRIP provider → host client in this node → `/dev/serial_rtk` → `rtk_rover` board → UM960 | yes: `RTKRESET` + `$GNRTK,ON*69`, the 4 s keep-alive, and the RTCM bytes once the board reports `$GNRTK,ON` |
| `none` | no corrections | no |
| `""` (default) | `auto` (above) | only while NTRIP owns the receiver |

`config_commands` (empty by default) is the only other thing this node ever writes.

### How the hardware is wired (from the vendor driver)

`/dev/serial_rtk` is not the UM960's own UART: it ends at the AT32 **`rtk_rover`**
board, which owns the UM960 and the LoRa module host MCU (`rtk_rover_m4`, Cortex-M4
driving a Semtech SX127x). The board passes the UM960 output through and intercepts
its own `$G...` commands (the strings `$GNCON`, `$GLIST`, `$GNRTK`, `RTKRESET`, `$GLORA`,
`LORARESET`, `$BRESET` are all in `mcu_decompile/rtk_rover/rtk_rover.strings.txt`).
Everything below was recovered from `libmower_gps_driver.so`
(`native_decompile/dec/libmower_gps_driver/libmower_gps_driver.so.c`); the command
literals' checksums were re-derived and match (`test_vendor_command_literals_match_the_xor_checksum`).

**LoRa / vendor base station** (`UnicoreGpsRos::setLoRa` @ 0x27ff1c, `setBand` @ 0x2806a4):

1. `set_lora(sn, addr, channel, area)` returns false if the serial port is not open.
2. Band: `area == ""` (what `base_ble` sends) → region = `sn[4:6]` (`sn` shorter than 6 →
   logged "sn error", band skipped); SN prefix `3001034903` is forced to region `01`.
   Region/area → command: `00`/`02` → `$GLIST,0*59`, `01` → `$GLIST,1*58`,
   `03` → `$GLIST,2*5B`, `F` → `$GLIST,F*2F`. An unknown `area` returns false.
3. Wait 0.5 s, then `$GNCON,<addr %04X>,<channel %02X>*<xor>` — the channel is in
   **hex** (the vendor's `std::hex` is still in effect). Result true; no ack is checked.
4. On every port (re)connect the vendor polls `$GNCON,0000,FF*4B`, `$GNVER,*64`,
   `$GHARD,F*32`; the board answers `$GNCON,<addr>,<channel>` (logged as "rtk hex addr").

So the LoRa radio is configured over the **same** UART, by the rover MCU, not by AT
commands from the host. This node reproduces those exact bytes
(`um960_gps_driver/lora.py`) but, because it has not been verified against the real
board, **`set_lora` is a stub by default**: it logs the commands it would write and
returns `result=false`. Set `lora_pairing_enabled: true` to actually write them (and the
on-connect `$GNCON,0000,FF*4B` query). Nothing else is needed for the LoRa path: the
base streams, the rover board injects, and the host only reads. `set_lora` returns
false whenever `correction_source != lora`.

**NTRIP** (`UnicoreGps::rtcmCallback`, `switchNRTK`, `setNrtkEnable`, `libntrip::NtripClient`):
the vendor writes the RTCM bytes unchanged into `/dev/serial_rtk` (their `ntrip.yaml`
comment: "rtk_input_port … to read GPGGA and to input RTCM from the ntrip server").
Before that it sends `RTKRESET` (only when NRTK is first enabled) and
`$GNRTK,ON*69`, and it only forwards RTCM while the board reports `$GNRTK,ON`; when the
board falls back to `OFF` it sends `RTKRESET`. No UM960-side `CONFIG COMx` / `RTKTYPE`
command is used: the UM960 is in `MODE ROVER` (vendor `serial_rtk_config.py`) and takes
RTCM 3 on its input port automatically.
What this node does in `ntrip` mode (the board handshake):

1. **Off → on** (the port opens, i.e. node start or a serial reconnect): write
   `RTKRESET\r\n` once, then `$GNRTK,ON*69\r\n`. The rover firmware compares the 12
   characters `$GNRTK,ON*69` exactly, so the command is sent verbatim.
2. **Keep-alive:** `$GNRTK,ON*69\r\n` again every `ntrip_keepalive_s` (4 s),
   unconditionally — the board drops back to LoRa when it hears nothing from the host
   for about 6 s.
3. **Board reports ON → OFF:** `RTKRESET` then `$GNRTK,ON*69` again (vendor `RTKReset()`
   on that edge plus its keep-alive). A first report of `OFF` (unknown → OFF) only waits
   for the keep-alive.
4. **RTCM gate:** RTCM from the caster is written only while the board's latest
   `$GNRTK,…` report is `ON` (in LoRa mode the board does not pass host bytes to the
   UM960). Until then it is held (dropped, counted as `rtcm_held_bytes`), a warning is
   logged at most every 10 s, and `/fix_status` shows `corr_flow=held`.
   `forward_rtcm_without_board_ack: true` skips the gate for bench tests without the board.
5. **Back to LoRa:** there is no OFF command. Switching to `correction_source: lora`
   (or `none`) and restarting the node just stops writing; without the keep-alive the
   board returns to LoRa by itself within ~6 s.

`ntrip_netmode` mirrors the vendor `ntrip_netmode`: `4g` binds the caster socket to
`usb0`, `wifi` to `wlan0` (`SO_BINDTODEVICE`, needs `CAP_NET_RAW` / root), `auto` or
`""` (default) leave it unbound. The vendor treated any other value as `usb0`; this node
warns and leaves it unbound. When empty it is taken from `ntrip_netmode` in the vendor file.

### Using NTRIP

**Owner settings file `/userdata/ros2/ntrip.yaml`** (`ntrip_settings_file`; mode 0600,
bind-mounted into `mower_humble`):

```yaml
enabled: true
host: "caster.example.net"
port: 2101
mountpoint: "MOUNT"
user: "user"
password: "secret"
```

* When the file exists it **wins** over the `ntrip_*` parameters and the vendor file
  (`/ntrip/status` `config_from` names the source). `enabled` decides whether
  `rtcm_source: auto` runs the client at all.
* **Editing from the GUI:** the NTRIP card (Settings → NTRIP) saves its fields to
  `mowgli_robot.yaml` *and* pushes them live to `/um960_gps_driver` through the
  parameter bindings (the same `rosProvider` path the LoRa card uses for its
  `set_lora` service call). The driver writes every live change of `ntrip_host`,
  `ntrip_port`, `ntrip_mountpoint`, `ntrip_user`, `ntrip_password`, `ntrip_enabled`
  or `correction_source`/`rtcm_source` (`ntrip` → `enabled: true`, `lora`/`none` →
  `false`) into the file atomically, then reconnects. The GUI mountpoint picker
  uses the GUI backend's `/api/ntrip/sourcetable`; the driver offers the same in
  Python (`ntrip_client.fetch_sourcetable` / `parse_sourcetable`).
* A hand edit is picked up within ~1 s (mtime check on the 1 Hz status timer).
* Without the file the parameters (and the GUI's launch overlay) apply as before;
  the file is created on the first live change.
* The password is never logged or published (`describe()` and the save log show
  only `password set/empty`; `/ntrip/status` has `password_set`).

**Robustness.** NTRIP 1 (`HTTP/1.0`, `ICY 200 OK`) and 2 (`HTTP/1.1`, `Ntrip-Version`,
chunked); basic auth; `Ntrip-GGA` in the request plus the receiver's own GGA every
`ntrip_gga_interval_s` (10 s); exponential reconnect backoff 1 s → `ntrip_reconnect_max_s`
(30 s; straight to the ceiling after `401`/sourcetable answers); reconnect after
`ntrip_no_data_timeout_s` of silence. **RTCM validation** (`ntrip_validate_rtcm: true`):
the byte stream is re-framed (`0xD3`, 10-bit length, CRC-24Q) and only whole valid
frames are written to the receiver; junk and corrupt frames are dropped and counted
(`crc_errors`, `dropped_bytes`).

**`/ntrip/status`** (`std_msgs/String` JSON, 1 Hz, transient-local = latched): `rtcm_source`,
`active_source` (`ntrip`/`lora`/`none`), `enabled`, `configured`, `host`, `port`,
`mountpoint`, `user_set`, `password_set`, `config_from`, `state`
(`off/connecting/connected/streaming/reconnecting/auth_failed/bad_mountpoint/error`),
`connected`, `rate_bps`, `bytes_rx`, `rtcm_age_s` (age of the last valid frame),
`frames`, `frames_written`, `crc_errors`, `dropped_bytes`, `message_types`, `gga_sent`,
`gga_age_s`, `attempts`, `connects`, `retries` (consecutive failures), `backoff_s`,
`uptime_s`, `last_error`, `switches` (auto hand-overs), `rover_nrtk`,
`receiver_quality` / `receiver_solution` / `receiver_diff_age_s`.

```bash
ros2 topic echo --qos-durability transient_local /ntrip/status std_msgs/msg/String
```

GGA uploaded to the caster: the receiver's last `GGA` with a position (≤ 5 s old);
otherwise one synthesized from the current fix (e.g. binary BESTNAV only), otherwise
the fallback position, otherwise nothing.

**Vendor credentials file.** The vendor app stored the caster in
`/userdata/mower/ntrip.yaml` (`ntrip_enable`, `ntrip_ip`, `ntrip_port`, `ntrip_user`,

`ros2_port_handoff/12_excluded_secrets_identity/userdata/ntrip.yaml`). When `ntrip_host`
is empty the node fills host/port/mountpoint/user/password from that file, and its
`ntrip_enable: true` enables NTRIP for `rtcm_source: auto` (both only when
`/userdata/ros2/ntrip.yaml` does not exist).
In a container the directory `/userdata/mower` has to be mounted for this to work.

**Security.** Never commit caster credentials. Keep them in a separate params file
(`config/um960_secrets.yaml` is listed in `src/um960_gps_driver/.gitignore`) or in the
vendor file on the robot, readable by the service user only (`chmod 600`). The node never
logs or publishes the password. The credentials found in the vendor tree
(`ntrip_client/config/*.yaml`) must be treated as compromised.

### Checking it works

```bash
ros2 topic echo /fix_status
# um960=connected solution=NARROW_INT ... diff_age=0.8s station=0451
#   corr_src=ntrip corr=streaming corr_flow=active corr_age=0.4s corr_rate=410B/s age=0.03s
ros2 topic echo /gps/corrections      # JSON: state, bytes_rx, rate_bps, frames,
                                      # crc_errors, message_types, gga_sent, rover_nrtk, ...
```

* `corr=` is the NTRIP client state: `connecting`, `connected` (caster accepted, no data
  yet), `streaming`, `reconnecting`, `auth_failed`, `bad_mountpoint`, `error`, `off`;
  `lora` in LoRa mode.
* `corr_flow=active` means a CRC-24Q-valid RTCM 3 frame arrived within
  `corrections_stale_s` (NTRIP) or the receiver's differential age is that fresh (LoRa).
* RTK is working when `solution=` / `quality=` reaches `NARROW_INT` / `RTK_FIXED`
  (float: `NARROW_FLOAT` / `RTK_FLOAT`) and `diff_age` stays small. `solution=SINGLE` with
  `corr_flow=active` means corrections arrive but the receiver does not use them
  (wrong datum/mountpoint, base too far away).
* `corr_flow=held` means RTCM arrives but the rover board has not reported
  `$GNRTK,ON`, so nothing is forwarded — check `rover_nrtk` / `rtcm_gate` /
  `rtcm_held_bytes` in `/gps/corrections`.
* `mower_gui_bridge` turns the tokens into `GnssStatus.correction_source`,
  `correction_transport_status`, `correction_flow_status`, `corrections_active`,
  `correction_age_s` (receiver `diff_age` preferred) for the MowgliNext GUI.

## Notes and caveats

* The vendor's driver is ROS 1 and links a private `libmower_gps_driver.so`. Its message
  definitions survive in `03_ros_interfaces/mower_gps_msgs` (`UnicoreNav.msg`,
  `UnicoreMessageHeader.msg`, `Info.msg`, `Gga.msg`, `Gsv.msg`) and were used here to
  confirm the BESTNAV field layout and the position/solution status enumerations.
* The vendor `.msg` comments for `UnicoreNav` contradict each other on two offsets
  (`undulation` at `H+32` on one line, `datum id` at `H+36`, and `ext sol stat` at `H+69`).
  This driver decodes `undulation` at `H+56` and `datum id` at `H+60`, which matches the
  UM960 manual's BESTNAV layout. Confirm against a real capture before trusting it: the
  field is only carried through for reference, it does not affect anything published.
* `NavSatFix.altitude` is the receiver's geoid height. BESTNAV also carries `undulation`
  (parsed, kept in the fix state) — subtract it if a consumer needs ellipsoidal height,
  and note the datum id (61 = WGS84) alongside it.
* There is no `TimeReference` publisher, so `/use_sim_time` does nothing here and
  `NavSatStatus.service` is hard-coded to GPS+GLONASS+Galileo+Compass. Both are worth
  revisiting when the localization fusion node lands.
* Heading from `GPHPR` is the receiver's own heading estimate (needs motion or dual
  antenna); falling back to the track angle means a stationary machine reports its last
  heading, not zero.
